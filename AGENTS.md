## Tech stack

.NET 10 · C# · ASP.NET Core Web API (controllers) · EF Core 10 + Npgsql · PostgreSQL 18 · SignalR · Hangfire (PostgreSQL storage) · xUnit + Testcontainers (real PostgreSQL; never the EF in-memory provider).

Web: Next.js (App Router) + TypeScript · Tailwind CSS v4 · React Query via the orval-generated `packages/api-client` · next-intl (fa/en, RTL) · PWA · Vitest + Playwright.

Monorepo: Nx + pnpm (`@nx/dotnet`, `@nx/next`, `@nx/playwright`). Hosting: API + PostgreSQL on a VPS with Dokploy; web on Liara. Full table and reasons: [docs/02-architecture.md §2.7](docs/02-architecture.md#27-technology-choices), [ADR-018](docs/09-decisions.md#adr-018). Not in the MVP: Redis, object storage, BullMQ, Nx Cloud, Expo, Tauri (see §2.10 for when to add them).

## Solution layout

```
apps/api/src/Inventory.Domain          entities, invariants, domain services (no EF, no ASP.NET)
apps/api/src/Inventory.Application     use cases per module
apps/api/src/Inventory.Infrastructure  EF Core, configurations, migrations, report SQL, Hangfire jobs
apps/api/src/Inventory.Api             controllers, DTOs, auth, OpenAPI, SignalR hubs
apps/api/tests/Inventory.UnitTests, apps/api/tests/Inventory.IntegrationTests
apps/web                               Next.js app (admin + sales screen PWA)
packages/api-client                    generated by orval from the API's OpenAPI; never edit by hand
packages/utils, packages/ui-web, packages/config
```

Dependencies: Api → Application → Domain; Infrastructure → Application/Domain. Thin controllers. The web app holds no business rules and runs no jobs: every write goes through the API.

```bash
pnpm nx dev web
pnpm nx affected -t lint test build e2e    # what CI runs

dotnet ef migrations add <Name> --project apps/api/src/Inventory.Infrastructure --startup-project apps/api/src/Inventory.Api
```

Nx target names come from the plugins once the workspace is created; adjust these commands to match `nx show projects` then.

## Non-negotiable rules (details in the docs)

1. One `items` table; composition goes through versioned `recipes` + `recipe_lines` (parent → component).
2. Stock changes only by appending `stock_movements` under an `inventory_operations` header, in **one transaction**, updating `stock_balances` in the same transaction. Never UPDATE or DELETE ledger rows; fix mistakes with a reversal.
3. Lock balance rows `FOR UPDATE` in item-id order inside stock operations.
4. Weighted average cost; production output cost = cost of the components consumed.
5. Reject negative stock unless `business_settings.allow_negative_stock`.
6. No circular recipes (graph check in the application; self-reference also blocked by a DB check).
7. `decimal` for all money and quantities; UTC timestamps; UUID v7 keys.
8. Archive items with history; hard-delete only items without history.
9. Every INV-xx rule in docs/04 gets a test; error codes match the catalogue.

## Conventions

Nullable on, warnings as errors, async + `CancellationToken`, `IEntityTypeConfiguration<T>` (not annotations), ProblemDetails with a stable `code`, Conventional Commits.
